# Дорожная карта развития плагина (ROADMAP)

Этот документ описывает стратегический план развития плагина **@lotargo/memory_plugin**. Наша цель — сохранить плагин легковесным, быстрым и не требующим нативной C++ компиляции, добавив при этом надежную облачную синхронизацию для работы на нескольких устройствах.

В качестве основного облачного провайдера для распределенной базы данных SQLite выбран сервис **Turso** (на базе технологии **libsql**), предоставляющий сверхбыстрый глобальный доступ по HTTP. В качестве резервной инфраструктуры (failover) заложена связка **Fly.io + LiteFS**.

---

## 1. Режимы работы с базой данных (Operational Modes)

Плагин будет поддерживать три независимых конфигурационных режима работы, настраиваемых через интерактивный CLI или файл конфигурации:

1.  **`only-local` (Только локальный)**
    *   **Описание**: Полностью приватный автономный режим (текущее поведение).
    *   **Принцип работы**: Все Markdown-блокноты (Layer 1) и векторы/символы в SQLite (Layer 2) хранятся исключительно на локальном диске пользователя под `~/.config/opencode/memory/`. Внешние сетевые запросы отсутствуют (за исключением первоначального скачивания весов модели из кэша HuggingFace CDN).
    *   **Кому подходит**: Для работы с конфиденциальным кодом и коммерческой тайной, а также в условиях отсутствия интернета.

2.  **`only-cloud` (Только облачный)**
    *   **Описание**: Полностью облачный бессерверный режим без локального кэширования.
    *   **Принцип работы**: Данные блокнота и векторы считываются и записываются напрямую в базу данных Turso в реальном времени. Локально хранятся только веса ONNX модели эмбеддингов для локального кодирования на клиенте.
    *   **Кому подходит**: Для сверхлегких контейнеров и окружений с ограниченным объемом дисковой памяти (например, Google Jules), где локальные файлы могут стираться между сессиями.

3.  **`hybrid-sync` (Локальный с фоновой синхронизацией)**
    *   **Описание**: Оптимальный гибридный режим, сочетающий максимальную скорость и резервное копирование.
    *   **Принцип работы**: Чтение и запись выполняются мгновенно в локальную SQLite БД. Специальный легковесный фоновый процесс (или интервальный воркер) асинхронно синхронизирует локальные изменения с облачной базой Turso. Блокноты Markdown синхронизируются через хранение их содержимого в текстовых полях или BLOB-ах в БД.
    *   **Кому подходит**: Для разработчиков, работающих на нескольких устройствах (например, домашний ПК и рабочий ноутбук), обеспечивая отсутствие задержек на запросы к сети при генерации ответов ИИ.

## 2. Безопасная авторизация через браузер (Browser-Based OAuth / Device Flow)

Для бесшовного и безопасного подключения к облаку Turso процесс авторизации будет организован по современным стандартам:

1.  **Команда запуска авторизации**:
    *   В CLI добавляется раздел `[CLOUD] Login to Turso Cloud`.
    *   Также доступна отдельная консольная команда:
        ```bash
        memory_plugin login
        # или через npx
        npx @lotargo/memory_plugin login
        ```
2.  **Процесс авторизации (Device Authorization Flow / Loopback)**:
    1.  Плагин делает запрос к нашему легковесному серверу авторизации, генерирует уникальный токен сессии и локально запускает временный HTTP-сервер ожидания на случайном порту (например, `http://localhost:48900/callback`).
    2.  Плагин автоматически открывает системный браузер пользователя по ссылке авторизации (например, `https://auth.lotargo.com/login?device_id=...`).
    3.  Пользователь авторизуется в браузере (через GitHub, Google или email).
    4.  После успешного входа облачный сервер перенаправляет браузер на локальный loopback адрес `http://localhost:48900/callback?token=...`.
    5.  Локальный сервер плагина принимает токен, глушит соединение, завершает свою работу и выводит в терминал сообщение об успешном входе.

3.  **Шифрование и хранение токенов**:
    *   Полученный сессионный токен (и секреты подключения к Turso Database URL) шифруется локально на диске с использованием симметричного алгоритма **AES-256-GCM**.
    *   В качестве ключа шифрования (KDF) используется уникальный аппаратный хэш машины (сочетание MAC-адреса первой сетевой карты, серийного номера процессора и имени пользователя), генерируемый библиотекой без передачи его в сеть. Это предотвращает простое копирование файла конфигурации на другую машину с целью кражи токена.

4.  **Деавторизация (Выход из системы)**:
    *   Выход выполняется через CLI меню `[CLOUD] Logout` или команду:
        ```bash
        memory_plugin logout
        ```
    *   При деавторизации зашифрованный файл токенов физически стирается с диска, локальные сессии инвалидируются, а режим работы принудительно переключается в `only-local`.

## 3. Резервная облачная инфраструктура (Failover Strategy): Fly.io + LiteFS

Turso является невероятно стабильной СУБД, однако для обеспечения 100% отказоустойчивости корпоративного уровня предусмотрен резервный план миграции:

*   **Что такое LiteFS?** LiteFS от Fly.io — это предохранитель уровня FUSE-системы, который перехватывает системные вызовы записи в SQLite и реплицирует их между узлами по сети.
*   **Архитектура резервного копирования**:
    *   Если шлюз Turso становится недоступен по таймауту (>10 секунд) в течение 3 попыток подряд, плагин временно переключается на запасной endpoint (запасную реплику базы данных, развернутую в кластере Fly.io с LiteFS).
    *   Пользователь видит ненавязчивое предупреждение в логах MCP-сервера: `[WARN] Turso is temporarily unreachable. Switching to LiteFS failover replica...`.
    *   Все операции записи аккумулируются на Fly.io, а после восстановления основного кластера Turso фоновый скрипт производит сверку и слияние инкрементальных изменений.

## 4. Этапы разработки (Roadmap Phases)

### Этап 1: Облачный слой (libsql) и CLI Авторизация (Текущий квартал)
- [x] Интеграция легковесного JS-драйвера `@libsql/client` (он не требует компиляции C++, так как работает по протоколу WebSocket/HTTP, сохраняя философию Zero-Docker).
- [x] Разработка модуля авторизации `memory_plugin login` / `logout` с loopback-сервером и шифрованием AES-256-GCM.
- [x] Добавление конфигурационных параметров режимов (`only-local`, `only-cloud`, `hybrid-sync`) в `config_manager.js`.

### Этап 2: Реализация режимов синхронизации (Текущий квартал)
- [x] **Реализация Only-Cloud**: Направление всех SQL-запросов (таблицы документов, секций, микро-чанков, графов и связей) в удаленный веб-сокет Turso.
- [x] **Реализация Hybrid-Sync**: Разработка фонового демона репликации. При изменении данных локально (например, вызов `remember` или `ingest_document`), изменения записываются в локальную SQLite, а в фоновую очередь добавляется задача синхронизации. Очередь обрабатывается асинхронно, не блокируя основной поток выполнения Node.js.

### Этап 3: Отказоустойчивость и Расширенный Парсинг (Перспективный этап)
- [ ] Развертывание резервного кластера на Fly.io + LiteFS, интеграция логики автоматического переключения (Circuit Breaker) в клиенте плагина.
- [ ] Добавление легковесных парсеров символов кода для других популярных языков (Python, Go, Rust, C++) в модуль `graph_extractor.js` для построения еще более качественного графа связей базы знаний (Layer 3).
