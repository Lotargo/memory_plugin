# Архитектурная идея: Decoupled & Policy-Driven RAG

> **Суть идеи:** Разделить _пространство поиска_ (векторная БД) и _пространство контекста_ (SQL / Key-Value хранилище). Векторная база используется как «Умное оглавление», а фактические данные отдаются LLM на основе правил, зашитых в метаданные каждого чанка.

---

### Проблема текущего подхода (Naive RAG)

- **Таблицы:** Векторизация сырых таблиц ломает косинусное сходство — эмбеддинг-модели плохо понимают матрицы чисел и столбцы.
- **Код:** Нарезка кода по фиктивному лимиту токенов рвет синтаксис (AST) и скрывает контекст (импорты, классы).
- **Шум и разрывы:** Маленький чанк точен для поиска, но мал для ответа. Большой чанк содержит много шума и снижает точность поиска (Precision).

---

### Архитектурная гипотеза

Если векторизовать **не сами данные, а их смысловые аннотации/сигнатуры**, а оригинальные структуры хранить в реляционной БД и подтягивать по динамическим правилам (Policies), то:

1. **Precision поиска вырастет**, так как поиск идет по чистым текстовым описаниям/микро-чанкам.
2. **Faithfulness генерации (отсутствие галлюцинаций) вырастет**, так как LLM получает цельный, не поврежденный нарезкой объект (полную таблицу, цельный класс кода).

---

### Ключевые компоненты концепции

#### 1. Двухуровневое хранилище (Dual-Storage)

- **Vector Store (Индекс / Оглавление):** Хранит только эмбеддинги _описаний таблиц_, _docstring-ов кода_, _заголовков_ или _микро-чанков_.
- **Truth Store (SQL / Key-Value / S3):** Хранит нетронутые исходные объекты — Markdown-таблицы, сырой SQL, файлы кода целиком, полнотекстовые родительские документы.

#### 2. Метаданные как «Правила Сборки» (Policy-Driven Retrieval)

Каждый вектор в ВБД содержит инструкцию для Orchestrator'а о том, как обработать этот результат при совпадении:

- **Тип `table_summary`:** Не передавать сам текст чанка в LLM ➔ Сходить в SQL по `table_id` ➔ Забрать цельную таблицу.
- **Тип `code_signature`:** Сходить в хранилище ➔ Забрать функцию вместе с импортами и контекстом класса.
- **Тип `micro_chunk`:** Забрать из SQL соседние чанки (окно $N$ до и после) или родительский документ.

#### 3. Умный оркестратор (Post-Processing & Deduplication)

Перед передачей контекста в LLM пайплайн:

1. Считывает `policy` из найденных векторов.
2. Дедуплицирует запросы (если 3 найденных чанка ведут к одной и той же таблице, таблица запрашивается из SQL только **один** раз).
3. Формирует чистый контекст без дублей и рваных фрагментов.

---

### Как измерить успех эксперимента (Метрики)

Для сравнения текущей версии RAG с этой концепцией:

1. **Table/Code Retrieval Accuracy:** Процент случаев, когда система смогла извлечь _правильную_ таблицу или функцию на сложный запрос.
2. **Hallucination Rate (Faithfulness):** Количество ошибок в цифрах/данных при ответах по таблицам.
3. **Context Redundancy:** Объём лишнего «мусорного» текста, попадающего в промпт.

---

### Резюме для внедрения

- **Не резать:** Таблицы и код не режутся на чанки.
- **Не векторизовать сырое:** Векторизуются описания и метаданные.
- **Управлять через правила:** Метаданные управляют расширением контекста.
