# Дорожная карта расширения парсинга кода (ROADMAP: MULTILINGUAL GRAPHRAG LITE)

Этот документ описывает стратегический план развития модуля **GraphRAG Lite** в рамках плагина **@lotargo/memory_plugin**. Наша цель — расширить возможности извлечения кодовых символов (классов, функций, интерфейсов, структур) за пределы текущей поддержки JavaScript/TypeScript на другие популярные языки программирования: **Python**, **Go**, **Rust** и **C++**.

---

## 1. Философия и технологические ограничения

Главная ценность плагина — **Zero-Docker / Zero-C++** (отсутствие необходимости компиляции бинарных модулей через `node-gyp`). Это гарантирует, что плагин мгновенно устанавливается на любую платформу (Windows, macOS, Linux).

Поэтому мы осознанно **отказываемся** от использования тяжелых бинарных парсеров (таких как компилируемые биндинги к Tree-Sitter). Вместо этого в качестве технологической основы мы выбираем:
1.  **Высокооптимизированные многострочные регулярные выражения (RegEx)** со специализированными флагами для быстрого лексического сканирования.
2.  **Легковесные текстовые токенизаторы** (на чистом JavaScript), выполняющие последовательный разбор ключевых слов (State-Machine Regex Lexers).

Этот подход гарантирует нулевые накладные расходы по памяти и процессорному времени, высокую скорость индексации и 100% переносимость.

---

## 2. Спецификация парсинга по языкам

Для каждого языка настраивается свой набор правил извлечения сущностей, которые затем регистрируются в SQLite-таблице `graph_edges` для связывания микро-чанков кода (Layer 3).

### 1. Python (`.py`)
*   **Что парсим**:
    *   Объявления классов: `class Name(Parent):`
    *   Объявления функций и методов (включая асинхронные): `def name(args):` и `async def name(args):`
    *   Декораторы (для контекста): `@decorator`
*   **Пример регулярного выражения**:
    *   Классы: `/class\s+([a-zA-Z0-9_]+)/g`
    *   Функции: `/async\s+def\s+([a-zA-Z0-9_]+)|def\s+([a-zA-Z0-9_]+)/g`

### 2. Go (`.go`)
*   **Что парсим**:
    *   Структуры (Structs): `type Name struct`
    *   Интерфейсы (Interfaces): `type Name interface`
    *   Функции и методы (с извлечением ресиверов): `func name(args)` или `func (r *Receiver) name(args)`
*   **Пример регулярного выражения**:
    *   Структуры/Интерфейсы: `type\s+([a-zA-Z0-9_]+)\s+(struct|interface)`
    *   Функции/Методы: `func\s+(?:\([^)]+\)\s+)?([a-zA-Z0-9_]+)\s*\(`

### 3. Rust (`.rs`)
*   **Что парсим**:
    *   Структуры: `struct Name` или `pub struct Name`
    *   Перечисления: `enum Name` или `pub enum Name`
    *   Трейты (Traits): `trait Name`
    *   Блоки реализации: `impl Name` или `impl Trait for Name` (позволяет связывать функции с их структурами)
    *   Функции: `fn name(args)` или `pub fn name(args)`
*   **Пример регулярного выражения**:
    *   Структуры/Энумы/Трейты: `(?:pub\s+)?(?:struct|enum|trait)\s+([a-zA-Z0-9_]+)`
    *   Функции: `(?:pub\s+)?(?:async\s+)?fn\s+([a-zA-Z0-9_]+)`

### 4. C++ (`.cpp`, `.h`, `.hpp`)
*   **Что парсим**:
    *   Классы и структуры: `class Name` или `struct Name`
    *   Пространства имен (Namespaces): `namespace Name`
    *   Методы и функции (включая сигнатуры в заголовочных файлах).
*   **Пример регулярного выражения**:
    *   Классы/Структуры: `(?:class|struct)\s+([a-zA-Z0-9_]+)`
    *   Функции/Методы: `([a-zA-Z0-9_]+)\s*\([^)]*\)\s*(?:const)?\s*[{;]` (с фильтрацией ключевых слов вроде `if`, `while`, `switch`).

## 3. Архитектура интеграции в GraphRAG Lite

Извлеченные символы встраиваются в существующую трехслойную структуру связей плагина:

1.  **Индексация документа (Pipeline Ingestion)**:
    При вызове `ingest_document` файл анализируется по расширению. Если расширение соответствует `.py`, `.go`, `.rs`, `.cpp`, `.h`, запускается соответствующий языковой экстрактор.
2.  **Заполнение графа (SQLite Graph Populating)**:
    Найденные имена символов сохраняются в таблицу `graph_edges` со связью типа `DEFINES` с соответствующим идентификатором микро-чанка (`section_id` / `chunk_id`).
3.  **Гибридный поиск (Retrieval & Symbol Boosting)**:
    При вызове `query_knowledge_base` поисковый запрос пользователя анализируется на точное или нечеткое совпадение с именами известных символов в графе. В случае совпадения, релевантность соответствующих чанков кода искусственно повышается (Symbol Boosting), а сами символы выводятся в блоке `Defined Symbols` в результатах поиска.

## 4. Этапы разработки (Roadmap Phases)

### Этап 1: Создание языковых экстракторов (Phase 1: Lexical Extractors)
*   Разработка изолированных модулей парсинга для каждого языка программирования внутри папки `mcp-server/graph/extractors/` (например, `python_extractor.js`, `go_extractor.js`, и т.д.).
*   Написание детальных unit-тестов на базе Vitest/Node-assert для проверки точности извлечения символов на реальных фрагментах кода Python/Go/Rust/C++.

### Этап 2: Интеграция в конвейер GraphRAG Lite (Phase 2: Pipeline Integration)
*   Модификация главного файла извлечения `mcp-server/graph/graph_extractor.js` для маршрутизации файлов по расширениям.
*   Реализация автоматического связывания структур Rust/Go с их методами (например, парсинг блоков `impl` и связывание методов со структурой-владельцем через ребро графа `METHOD_OF`).

### Этап 3: Оптимизация поиска и ранжирования (Phase 3: Search Optimization)
*   Тюнинг весов Symbol Boosting в формуле гибридного ранжирования (RSF Alpha баланс).
*   Проведение нагрузочных тестов (Stress-Ingestion) на крупных репозиториях для замера влияния регулярных выражений на общее время индексации проекта (целевой показатель — не более 1.5 секунд на 1000 строк кода).
