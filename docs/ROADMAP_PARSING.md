# Дорожная карта расширения парсинга кода и документов (ROADMAP: MULTILINGUAL & DOCUMENT GRAPHRAG LITE)

Этот документ описывает стратегический план развития модуля **GraphRAG Lite** в рамках плагина **@lotargo/memory_plugin**. Наша цель — расширить возможности извлечения кодовых символов (классов, функций, интерфейсов, структур, модулей) и интегрировать поддержку популярных офисных и текстовых форматов документов (**PDF**, **DOCX**, **XLSX**, **CSV**).

---

## 1. Философия и технологические ограничения

Главная ценность плагина — **Zero-Docker / Zero-C++** (отсутствие необходимости компиляции бинарных модулей через `node-gyp`). Это гарантирует, что плагин мгновенно устанавливается на любую платформу (Windows, macOS, Linux).

Поэтому мы осознанно **отказываемся** от использования тяжелых бинарных парсеров (таких как компилируемые биндинги к Tree-Sitter или нативные утилиты PDF/Docx). Вместо этого в качестве технологической основы мы выбираем:
1.  **Высокооптимизированные многострочные регулярные выражения (RegEx)** со специализированными флагами для быстрого лексического сканирования языков программирования.
2.  **Легковесные текстовые токенизаторы** (на чистом JavaScript), выполняющие последовательный разбор ключевых слов.
3.  **Pure-JS библиотеки** для разбора бинарных форматов файлов, которые работают в любой Node.js среде без внешних зависимостей.

Этот подход гарантирует нулевые накладные расходы по памяти и процессорному времени, высокую скорость индексации и 100% переносимость.

## 2. Спецификация парсинга кода по языкам

Для каждого языка настраивается свой набор правил извлечения сущностей, которые затем регистрируются в SQLite-таблице `graph_edges` для связывания микро-чанков кода (Layer 3) со знанием о символах.

Мы значительно расширили первоначальный список языков, добавив полную поддержку следующих технологий:

### 1. Python (`.py`)
*   **Что парсим**: Классы (`class Name`), функции/методы (`def name`, `async def name`).
*   **Регулярные выражения**:
    *   Классы: `/class\s+([a-zA-Z0-9_]+)/g`
    *   Функции: `/async\s+def\s+([a-zA-Z0-9_]+)|def\s+([a-zA-Z0-9_]+)/g`

### 2. Go (`.go`)
*   **Что парсим**: Структуры (`type Name struct`), интерфейсы (`type Name interface`), функции (`func name`) и методы с ресиверами (`func (r *Rec) name`).
*   **Регулярные выражения**:
    *   Структуры/Интерфейсы: `/type\s+([a-zA-Z0-9_]+)\s+(?:struct|interface)/g`
    *   Функции/Методы: `/func\s+(?:\([^)]+\)\s+)?([a-zA-Z0-9_]+)\s*\(/g`

### 3. Rust (`.rs`)
*   **Что парсим**: Структуры (`struct Name`), перечисления (`enum Name`), трейты (`trait Name`), функции (`fn name`).
*   **Регулярные выражения**:
    *   Типы: `/(?:pub\s+)?(?:struct|enum|trait)\s+([a-zA-Z0-9_]+)/g`
    *   Функции: `/(?:pub\s+)?(?:async\s+)?fn\s+([a-zA-Z0-9_]+)/g`

### 4. C++ (`.cpp`, `.h`, `.hpp`, `.cc`, `.cxx`)
*   **Что парсим**: Классы и структуры (`class Name`, `struct Name`), пространства имен (`namespace Name`), функции/методы.
*   **Регулярные выражения**:
    *   Классы/Структуры: `/(?:class|struct)\s+([a-zA-Z0-9_]+)/g`
    *   Функции/Методы: `/([a-zA-Z0-9_]+)\s*\([^)]*\)\s*(?:const)?\s*[{;]/g` (с фильтрацией ключевых слов `if`, `while`, `switch` и т.д.).

### 5. Java & Kotlin (`.java`, `.kt`)
*   **Что парсим**: Классы (`class Name`), интерфейсы (`interface Name`), методы, а в Kotlin — также функции верхнего уровня (`fun name`).
*   **Регулярные выражения**:
    *   Классы/Интерфейсы: `/(?:class|interface|record|enum)\s+([a-zA-Z0-9_]+)/g`
    *   Методы/Функции: `/(?:public|protected|private|static|\s)*[\w<>\[\]]+\s+([a-zA-Z0-9_]+)\s*\([^)]*\)\s*(?:throws\s+[\w,\s]+)?\s*[{;]/g` (Java) и `/(?:pub\s+)?fun\s+([a-zA-Z0-9_]+)/g` (Kotlin).

### 6. C# (`.cs`)
*   **Что парсим**: Классы, интерфейсы, структуры, рекорды, методы.
*   **Регулярные выражения**:
    *   Типы: `/(?:class|interface|struct|record)\s+([a-zA-Z0-9_]+)/g`
    *   Методы: `/(?:public|private|protected|internal|static|async|virtual|override|readonly)*\s*[\w<>\[\]]+\s+([a-zA-Z0-9_]+)\s*\([^)]*\)\s*[{;]/g`.

### 7. PHP (`.php`)
*   **Что парсим**: Классы, интерфейсы, трейты, функции.
*   **Регулярные выражения**:
    *   Типы: `/(?:class|interface|trait)\s+([a-zA-Z0-9_]+)/g`
    *   Функции: `/function\s+([a-zA-Z0-9_]+)/g`.

### 8. Ruby (`.rb`)
*   **Что парсим**: Модули (`module Name`), классы (`class Name`), методы (`def name`).
*   **Регулярные выражения**:
    *   Модули/Классы: `/(?:class|module)\s+([a-zA-Z0-9_:]+)/g`
    *   Методы: `/def\s+([a-zA-Z0-9_!?=]+)/g`.

## 3. Спецификация парсинга офисных документов и таблиц

Для интеграции документов (PDF, DOCX, XLSX, CSV) используются только pure-JS библиотеки. При этом применяется **гибридный подход** для баланса между читаемостью оригинальных документов и качеством векторного поиска.

### 1. Архитектура обработки документов
*   **PDF (`.pdf`)**: Используется библиотека `pdf-parse`. Текст извлекается постранично, очищается от лишних пробелов и управляющих символов и преобразуется в плоский Markdown-текст с разделением на логические абзацы.
*   **DOCX (`.docx`)**: Используется библиотека `mammoth`. Она производит чистую конвертацию структуры документа (заголовки, списки, абзацы) в структурированный Markdown.
*   **Таблицы XLSX/XLS (`.xlsx`, `.xls`) и CSV (`.csv`)**: Используется библиотека `xlsx` (SheetJS). Реализуется уникальный гибридный конвейер:
    *   **Сырой документ (для Blob Store)**: Вся таблица форматируется в классическую Markdown-таблицу (с разделителями `|` и заголовками). Это позволяет пользователю увидеть точную структуру документа при запросе оригинального контента.
    *   **Текстовые Чанки (для RAG/Векторов/FTS)**: Таблица преобразуется построчно в текстовые семантические блоки формата:
        ```text
        Запись из таблицы [Имя_файла] (Строка X):
        - Колонка1: Значение1
        - Колонка2: Значение2
        ```
        Это полностью устраняет проблему "векторного зашумления" разметкой Markdown-таблиц, при этом сохраняя четкую семантическую связь между ячейками одной строки для качественного семантического и полнотекстового поиска.

## 4. Этапы разработки (Roadmap Phases)

### Этап 1: Дополнение концепции и установка библиотек (Phase 1)
*   Документирование расширенной дорожной карты (выполнено).
*   Установка Pure-JS зависимостей: `npm install pdf-parse mammoth xlsx`.

### Этап 2: Интеграция парсеров документов в normalizer.js (Phase 2)
*   Добавление поддержки бинарных буферов (Buffer) в конвейер импорта `pipeline.js`.
*   Реализация конвертеров в `normalizer.js` для каждого нового формата файлов.
*   Реализация гибридного разбиения XLSX/CSV (Markdown для сырого блоба, построчный текст для чанкера).

### Этап 3: Расширение извлечения символов в graph_extractor.js (Phase 3)
*   Написание регулярных выражений и фильтрации зарезервированных слов для Python, Go, Rust, C++, Java/Kotlin, C#, PHP и Ruby.
*   Регистрация извлеченных символов в графе знаний RAG.

### Этап 4: Тестирование и валидация (Phase 4)
*   Создание тестов для проверки извлечения символов на различных языках программирования.
*   Создание сквозных интеграционных тестов для PDF, DOCX, XLSX и CSV файлов.
*   Запуск всех тестов проекта для подтверждения отсутствия регрессии.
